# تقرير تأمين API Heist Academy

**التاريخ:** 2026-08-29

**النطاق:** التطبيق المحلي في هذا المستودع، بما يشمل Flask API والواجهة وPostman وDocker

**المرجع:** OWASP API Security Top 10 — 2023

**الفرع:** `harden-owasp-api`

## الملخص التنفيذي

كان التطبيق مختبرًا تعليميًا متعمد الضعف، وكانت مسارات OWASP API Top 10 العشرة قابلة للاستغلال. أثبت اختبار تشغيل محلي مضبوط على قاعدة SQLite مؤقتة أن المسارات العشرة تكشف قيمة تعليمية حساسة عند استغلالها؛ أعادت تسعة مسارات `200` مع القيمة، وأعاد مسار الإعداد الخاطئ `500` مع القيمة داخل الخطأ.

أصبحت النسخة الافتراضية الآن **مُحصنة**: أزيلت قيم الاستغلال، وفُصلت صلاحيات الفريق عن المشرف، وربط الوصول للكائن بهوية موقعة، وطُبقت حدود صلبة للموارد والتدفقات، وأصبح SSRF مرفوضًا افتراضيًا، وأضيف توقيع HMAC ومنع replay للـ webhooks. كما عولجت أربع مشاكل إضافية في إدارة اللعبة والخصوصية.

نتيجة إعادة الاختبار النهائية:

```text
15 passed
No broken requirements found.
POSTMAN_JSON_VALID
```

فحص HTTP فعلي على خادم مؤقت أكد: health=`200`، إنشاء الفريق=`200` مع رمز، الملف المملوك=`200`، ملف آخر=`403`، debug probe=`404`، وCSP موجود دون رأس CORS مفتوح.

لم تُعدّل قاعدة المستخدم الموجودة `backend/heist.db` أثناء الاختبارات؛ استُخدمت قواعد مؤقتة، وحُذفت قاعدة خط الأساس المؤقتة بعد الانتهاء.

## واجهة الشرح بعد التأمين

- يمكن فتح بطاقات OWASP API Top 10 العشر مباشرة دون تسجيل فريق أو انتظار مؤقت أو الاعتماد على تقدم الجلسة القديمة.
- تعرض كل بطاقة: وصف الثغرة قبل الإصلاح، السبب الجذري، ضوابط التأمين، أسماء التغييرات البرمجية، وطلبات تحقق آمنة مع رمز HTTP المتوقع.
- التسجيل اختياري، ووظيفته الوحيدة إصدار Bearer token معزول عندما يحتاج الطالب إلى تجربة مسار محمي فعليًا.
- أزيلت آلية إدخال Flags من التدفق بعد التأمين؛ معيار النجاح الآن هو رفض الطلب الضار وإبقاء الطلب المشروع عاملًا.
- زر **إعادة عرض الدليل** يمسح حالة الواجهة والرمز من المتصفح فقط ولا يطلب Admin Token. بقي مسح قاعدة البيانات بالكامل عملية إدارية منفصلة ومحميّة.
- أضيف اختبار رجعي يثبت أن اكتمال الجلسة القديمة لا يمنع عرض الدليل أو إنشاء هوية اختبار، واختبار آخر يثبت اكتمال محتوى الشرح لكل البطاقات العشر.

## المنهجية وحدود التحقق

- تدقيق أبيض الصندوق لجميع مسارات Flask ومصادر البيانات ومخارج HTML.
- إثبات ديناميكي قبل الإصلاح باستخدام `Flask test_client` وقاعدة منفصلة، دون أي اتصال خارجي.
- اختبارات رجعية ديناميكية بعد الإصلاح لكل بند، إضافة إلى فحوص البنية والاعتماديات.
- لم يُشغّل Strix: Docker Desktop غير عامل، وأداة `strix` ومفاتيح LLM/Cloud غير متوفرة. لذلك فهذا تقرير تدقيق واختبار محلي موثق، وليس تقريرًا صادرًا عن Strix.
- لم يُبنَ Docker image بسبب توقف Docker daemon؛ تم تدقيق Dockerfile وCompose ساكنًا، بينما اختُبر التطبيق مباشرة عبر Python.

| API5 | `DELETE /api/admin/users` بلا مصادقة | `200` وكشف القيمة |

## التقرير التفصيلي حسب OWASP

### API1:2023 — Broken Object Level Authorization (BOLA)

- **الخطورة قبل الإصلاح:** عالية.
- **السبب الجذري:** كان المعرّف الموجود في URL كافيًا للوصول إلى أي سجل، دون ربطه بهوية طالب الطلب.
- **الأثر:** قراءة ملفات وخصائص تخص مستخدمين آخرين.
- **الإصلاح:** تسجيل الفريق ينشئ حسابًا معزولًا ورمز JWT قصير العمر. يحمل الرمز `team_id` و`user_id` وnonce، ويُرفض الطلب إذا لم يطابق `user_id` معرّف المسار. لم تعد الخصائص الداخلية تُدمج في الاستجابة.
- **إعادة الاختبار:** الملف المملوك `200`، ملف فريق آخر `403`، والطلب بلا رمز `401`. حالة الفريق الآخر تعيد `403`.

### API2:2023 — Broken Authentication

- **الخطورة قبل الإصلاح:** حرجة.
- **السبب الجذري:** عند فشل التحقق من توقيع JWT كان الخادم يعيد فك الرمز مع `verify_signature=False` ويثق بدور `admin`.
- **الأثر:** انتحال مشرف والوصول إلى وظائف إدارية.
- **الإصلاح:** تحقق إلزامي من HS256 والتوقيع و`issuer` و`audience` و`sub` و`iat` و`nbf` و`exp` ونوع الدور وnonce المخزن. أزيل sample token. فُصلت الإدارة إلى `X-Admin-Token` مستقل بمقارنة ثابتة الزمن، وتُعطل الإدارة إذا لم يُضبط السر.
- **إعادة الاختبار:** الرمز المزور والمنتهي `401`، ورمز الفريق على مسار المشرف `401`، ورمز المشرف الصحيح فقط يُقبل.

### API3:2023 — Broken Object Property Level Authorization

- **الخطورة قبل الإصلاح:** عالية.
- **السبب الجذري:** دمج جسم JSON كاملًا في كائن المستخدم (`user.update(data)`).
- **الأثر:** تغيير role أو balance أو خصائص غير مخصصة للمستخدم.
- **الإصلاح:** allowlist صريحة لـ `name` و`email` فقط، مع تحقق النوع والطول وصيغة البريد. تبقى `role` و`balance` خصائص خادم.
- **إعادة الاختبار:** إرسال `role` و`balance` يعيد `400` ويسمي الحقول المرفوضة؛ تحديث الاسم والبريد الصحيح `200` مع بقاء الدور `user` والرصيد دون تغيير.

### API4:2023 — Unrestricted Resource Consumption

- **الخطورة قبل الإصلاح:** متوسطة إلى عالية.
- **السبب الجذري:** حد ناعم يستمر في زيادة العداد، ثم يكافئ الاستمرار بعد عدد أعلى من الطلبات.
- **الأثر:** استهلاك CPU/قاعدة البيانات وتجاوز سياسة السرعة.
- **الإصلاح:** حد صلب ذري داخل معاملة SQLite، مرتبط بمعرّف فريق موثق، مع نافذة زمنية و`Retry-After`. أضيف حد 16 KiB لجسم الطلب، و`busy_timeout` وWAL للتعامل الآمن مع التزامن.
- **إعادة الاختبار:** أول خمسة طلبات `200`، وكل الطلبات اللاحقة في النافذة `429` دون تحول إلى نجاح أو كشف بيانات.

### API5:2023 — Broken Function Level Authorization

- **الخطورة قبل الإصلاح:** حرجة.
- **السبب الجذري:** وظيفة DELETE الإدارية بلا أي تحقق صلاحيات.
- **الأثر:** تنفيذ وظيفة عالية الامتياز من مستخدم مجهول.
- **الإصلاح:** decorator مركزي `require_admin` قبل منطق المسار، مع سر إدارة منفصل؛ العملية الحالية آمنة ولا تحذف أي سجل دون تحديد.
- **إعادة الاختبار:** بلا سر أو برمز فريق `401`، وبسر المشرف الصحيح `200` و`deleted=[]`.

### API6:2023 — Unrestricted Access to Sensitive Business Flows

- **الخطورة قبل الإصلاح:** عالية.
- **السبب الجذري:** قبول أي مبلغ، وعدم التحقق من الرصيد أو المستفيد أو التكرار أو سرعة التدفق؛ كما لم يكن إنشاء الفرق محدودًا.
- **الأثر:** تحويلات سالبة/آلية، تكرار العملية، واستنزاف التدفق بإنشاء حسابات آلية.
- **الإصلاح:** مبلغ صحيح بين 1 و100، تحقق مستفيد ورصيد، `Idempotency-Key`، حد عدد وقيمة تراكمية، وتنفيذ ذري داخل `BEGIN IMMEDIATE`. أضيف حد 20 تسجيلًا لكل عنوان/ساعة مع تخزين hash للعنوان بدل النص الخام.
- **إعادة الاختبار:** المبلغ السالب `400`، غياب idempotency key `400`، إعادة نفس المفتاح `200` بوصفها replay دون خصم ثانٍ، تجاوز 500 في النافذة `429`، والتسجيل رقم 21 `429`.

### API7:2023 — Server Side Request Forgery (SSRF)

- **الخطورة قبل الإصلاح:** عالية.
- **السبب الجذري:** قبول URL من العميل، ومحاكاة/السماح بوجهات metadata وloopback، ثم جلب أي URL خارجي.
- **الأثر:** الوصول إلى metadata أو خدمات داخلية وتسريب استجاباتها.
- **الإصلاح:** deny-by-default، HTTPS فقط، port 443، منع credentials وfragment، allowlist دقيقة، حل DNS والتحقق أن كل العناوين عامة، منع redirects، حد 8 KiB، وقبول `text/*` أو JSON فقط. أُغلق `/api/internal/flag` بـ`404`.
- **إعادة الاختبار:** metadata عبر HTTP `400`، و`https://example.com` غير المدرج `403`، والمسار الداخلي `404`؛ لم يجرِ أي طلب شبكة أثناء الاختبار.

### API8:2023 — Security Misconfiguration

- **الخطورة قبل الإصلاح:** عالية.
- **السبب الجذري:** debug endpoint يعيد traceback وقيمة حساسة؛ CORS مفتوح؛ أسرار افتراضية ثابتة؛ وخادم التطوير مستخدم في الحاوية.
- **الأثر:** كشف أسرار وبنية داخلية، وتوسيع مصدر الطلبات، وضعف إعداد النشر.
- **الإصلاح:** debug `404`، error handler عام، سر JWT عشوائي محلي أو إلزامي خارج loopback، إزالة Flask-CORS، وإضافة CSP وnosniff وDENY frame وReferrer/Permissions policies وno-store. Docker يستخدم Gunicorn ومستخدمًا غير root وread-only filesystem وcapabilities مسقطة.
- **إعادة الاختبار:** probe التصادم `404` دون traceback أو قيمة، رؤوس الحماية موجودة، ولا يوجد `Access-Control-Allow-Origin`، والمسار API غير المعروف يعيد JSON `404`.

### API9:2023 — Improper Inventory Management

- **الخطورة قبل الإصلاح:** عالية.
- **السبب الجذري:** بقاء `/api/v1/users` عاملًا مع بيانات أوسع من v2.
- **الأثر:** تجاوز ضوابط الإصدار الحالي وجرد مستخدمين عبر سطح منسي.
- **الإصلاح:** v1 يعيد `410 Gone` مع `Deprecation`, `Sunset`, ورابط successor دون بيانات. v2 يتطلب Bearer token ويعيد سجل المتصل فقط.
- **إعادة الاختبار:** v1 `410` بلا `users`، وv2 بلا مصادقة `401`، ومع المصادقة يعيد كائنًا واحدًا يخص الفريق.

### API10:2023 — Unsafe Consumption of APIs

- **الخطورة قبل الإصلاح:** عالية.
- **السبب الجذري:** الثقة المباشرة في event/payload والتحكم بالسلوك عبر كلمات خاصة، بلا مصادقة للمرسل أو منع replay.
- **الأثر:** معالجة أحداث مزورة أو معادة والتحكم في منطق التكامل.
- **الإصلاح:** HMAC-SHA256 على `<timestamp>.<raw_body>`، نافذة زمنية، مقارنة ثابتة الزمن، event allowlist، JSON محدود، وتخزين التوقيع المقبول لمنع replay.
- **إعادة الاختبار:** الطلب غير الموقع `401`، التوقيع الصحيح `202`، وإعادة نفس الطلب `409`.

## مشاكل إضافية عولجت

| المشكلة | الإصلاح | التحقق |
|---|---|---|
| إعادة ضبط كاملة بلا صلاحية | `X-Admin-Token` مطلوب | بلا سر `401` |
| انتحال فريق موجود | الرمز مرتبط بـteam id وnonce؛ تحديث التسجيل يتطلب ملكية الفريق | بلا رمز `401` وبرمز فريق آخر `403` |
| كشف حالة فريق | `require_team` ومطابقة اسم المسار بهوية الرمز | بلا رمز `401` وعبر فريق آخر `403` |
| كشف أسماء الأعضاء في leaderboard | استجابة مصغرة: name, points, total_time_seconds فقط | لا تظهر members أو ids أو nonce |
| Stored/DOM XSS في الواجهة | `textContent` للعناصر الديناميكية وHTML escaping للقالب المتبقي مع CSP | فحوص مصدر رجعية واختبار حمولة الأسماء |
| أسرار/اعتماديات قديمة | إزالة السر الافتراضي وFlask-CORS؛ تحديث Flask/PyJWT/Werkzeug/Gunicorn | `pip check` ناجح |

## تغييرات التشغيل والاعتماديات

- `Flask 3.1.3`
- `PyJWT 2.13.0`
- `Werkzeug 3.1.8`
- `gunicorn 26.0.0`
- إزالة `flask-cors` لأن الواجهة وAPI من نفس الأصل.
- Postman collection تحفظ team token وprofile id تلقائيًا، وتوقّع webhook عند ضبط `webhookSecret`.
- Bandit: لا نتائج. pip-audit: لا ثغرات معروفة في الاعتماديات المثبتة وقت الفحص.

## ضوابط يجب على المشغّل إكمالها

1. اضبط أسرارًا مستقلة عشوائية لا تقل عن 32 حرفًا، ولا تضعها في Git.
2. غيّر كل الأسرار إذا كانت نسخة قديمة مكشوفة قد شُغلت خارج جهاز محلي.
3. استخدم HTTPS عبر reverse proxy موثوق قبل أي وصول شبكي غير loopback.
4. اترك `DVAPI_FETCH_ALLOWLIST` فارغًا ما لم تكن ميزة الجلب ضرورية.
5. عند التوسع على عدة hosts، انقل rate limits وwebhook replay state إلى مخزن مشترك ذري مثل Redis/PostgreSQL.
6. بعد تشغيل Docker Desktop، أعد بناء الصورة وشغّل فحص Strix مستقلًا للحصول على تحقق ديناميكي إضافي للحاوية المنشورة.
